# Subway Architecture

> What `src/subway/` serves about the subway stations near the two campuses and the commute shuttle's stops, how a station and each of its platforms are identified, where their data comes from, how the tracker turns it into arrivals, and what adding a station or a provider touches. Read it before changing the network, the topology, a data source or the estimates.

## Context

Subway owns the real-time arrivals of the served stations: physical stations, each with one platform per line, Sungkyunkwan Univ. on line `1` (a Korail section), Hyehwa on line `4`, Sadang (lines `2` and `4`), Geumjeong (lines `1` and `4`, Korail sections) and `종로5가` (line `1`), where a journey boards or alights, and the commute shuttle's stops on lines `2`, `3` and `8` (Seoul Metro) on line `K1`, Suin–Bundang (Korail), and on line `D1`, Shinbundang (its own operator). It mirrors the operators' timetables as the `subway-timetables` dataset and, through a provider per jurisdiction, their live train positions and arrival rows; from both it keeps each platform's next trains in `subway_arrivals`, which the arrivals route serves per station. Lines, stations and platforms, with their labels, live in code; each platform's directions and the neighbor stops are the `subway-topology` dataset; each station's camera point is the `subway-station-coords` dataset; the timetables are generated by a script and pushed as the parted `subway-timetables` dataset.

| Field | App use |
| --- | --- |
| `station` | The station's slug, its name in the request language and its `coords`, the camera point the app opens the station's sheet on over the shared map, null with none; served and not rendered yet |
| `lines` | One entry per platform in the station's order: the line display data, the `platformId`, and the platform's own `generatedAt` (when its arrivals were computed, for a staleness label; the request time when the timetable alone is served) and directions; served and not rendered yet |
| `directions` | Up then down, each with its name, `previousStation` and `nextStation` in the request language and at most `MAX_TRAINS_PER_DIRECTION` trains; served and not rendered yet |
| `trains[]` | [ADR 0022](../decisions/0022-journey-and-call-spec.md)'s call plus `trainNo`: the instants the app counts down to against the server's clock (`meta.serverNow`), the basis (the stored source renamed), the status and stops away from the stored position (`toCallStatus`, `toCallStopsAway`), the run, the headsign and the first, last and express flags; the neighbor stations stay on the direction |

The root holds the module file, which binds the rate limiter for `subway`, the network (`SUBWAY_LINES`, `SUBWAY_STATIONS` and `SUBWAY_NETWORK` in `.constants`, `subwayNetwork`, `toNetworkIssues`, `toSubwayLine`; `subwayRegistryFile`, the shape of the registry the network and the topology join into), the provider seam (`SubwayProvider` and the shapes it hands over in `src/subway/subway.types.ts`) and `SubwayRepository`, which the tracker writes and the route reads. Everything after the seam does not depend on the provider: merging, delay, estimates, the stored state and the response.

- `stations/` holds `SubwayStationsService`, the door other modules list the served stations through: each one's slug, its title and its lines' display data, from the network, so the transit tab, `/bus/config` and the stop catalog's boot check read no dataset. `station-list/` serves them all as `GET /subway/stations`, the title and line display data in the request language, each with its coords from `station-coords/`, `null` without them and never a `503`: the points the app's shared map starts its camera at the user near.
- `topology/` holds `SubwayTopologyService`, the door to the stored `subway-topology`: `current()` answers `{ revision, registry }` on a dataset loader (a minute, and the last good value a day through failed reads); a served platform with no entry, an entry for no served platform and a previous or next stop with no name, which the route serves as `null`, are each logged at error once per revision (`subway.topology.platform_missing`, `.platform_unknown`, `.stop_unnamed`); never read, it throws `SUBWAY_TOPOLOGY_UNAVAILABLE`, an HTTP `503`, and `findCurrent()` answers null, for the journey door, whose rides then list no stops.
- `station-coords/` holds `SubwayStationCoordsService`, the door to the stored `subway-station-coords`: `findCoords(stationId)` answers a served station's coords on a dataset loader (a minute, and the last good value a day through failed reads), or null: never read, its cause logged at error (`subway.station_coords.missing`, `.invalid`, `.read_failed`), or a station the revision lacks, logged at warn once per revision (`subway.station_coords.station_missing`); a stored station the code does not serve is ignored (`.station_unknown`). It never answers a `503`: the coords are a documented degraded answer of [ADR 0013 D6](../decisions/0013-runtime-data-in-mongodb.md), and only a push is strict, refusing a served station without coords, a station the code does not serve and a point outside South Korea.
- `timetable/` holds the service-day rules and `findSubwayPlatform`, and reads `subway-timetables`: `SubwayTimetableService` is its door, each platform's schedule for the service day of an instant, and whether the instant is in the service window, which reads no dataset. Its manifest is a dataset loader's (a minute, the last good value a day through failed reads). A table is read only when a platform of its line is scheduled, once per part id, then held by key; a held table goes once a later service day needs another of its line, so a process holds at most one day type per line, one table per line, where every role parsed every table at import before, and an api replica whose arrival state is fresh holds none. A part that cannot be read leaves the held copy serving until a day after the manifest first named it, and is retried once a minute (`subway.timetables.part_missing`, `.part_invalid`, `.part_read_failed`); a served platform whose table the revision lacks is logged at error once per revision (`subway.timetables.table_missing`). Without a table one schedule throws `SUBWAY_TIMETABLES_UNAVAILABLE`, an HTTP `503`, naming the key, and the list leaves the platform out and carries that error. Its sub-module `departures/` holds `SubwayTimetableDeparturesService`, the journey's door ([ADR 0022, D6](../decisions/0022-journey-and-call-spec.md)): a ride's trains from its board platform to its alight one on the service day, joined within one table by the train's own row and across two by train number, each as the call this module's board serves for a timetable train, or, for a train the board platform's station board lists live or estimated, as that board's call (`SubwayArrivalsService.listPlatformCalls`) with the ride's first and last flags, timed by `toBoardTime` and its delay there carried to the alight as an estimate; after the day's last train, the next day's first, read once per ride and day so the held tables are not swapped on every poll.
- `estimate/` holds the delay and estimate rules; `SubwayEstimateService` is its door, and reads every countdown through `SubwayCountdownService` (`countdown/`), which remembers the countdown rows it was last handed, in the poller process, so a row repeating a train's countdown at a station counts from its first publication; it then decides whether each train counts it.
- `seoul-api/` and `seoul-trainmap/` each hold a client, its mapper to train events (and, for the API, countdown rows) and a service that is their door; neither names a platform, since each is handed the platform table of the line it reads. `SubwaySeoulTrainmapService` counts a line with no train as no train until its empty spell exceeds `MAX_EMPTY_LINE_MS`.
- `seoul/` holds `SubwaySeoulService`, which derives what it polls from the topology's registry once per revision, before any call or ceiling, so a never-read topology rejects the tick with nothing called (`toSeoulLines`: each line's numbering, its served platforms by `statnId` and its neighbors by name): `observeApi` makes one position call per line and one arrival call per station (`toSeoulStations`), `observeTrainMap` crawls the page of every line once, reads each line with a train map from its own blocks and stamps their events with the crawl time, and each upstream call first takes one from its source's daily ceiling (`config.subway.apiDailyCap`, `config.subway.trainMapDailyCap`). `SubwaySeoulPoller` registers `subway-seoul` and `subway-trainmap`, each on its own interval, each handing its upstream to the tracker. Each call of a tick settles apart; `SubwaySeoulPoller` tracks what answered, then rejects the tick with the first failure.
- `tracking/` holds `SubwayTrackingService`. Inside the service window it observes the upstream it is handed, merges the events into each platform's train histories, reading an express's event at a station it passes as its departure from its last stop before it, keeps each source's latest countdown rows, estimates each direction's next `MAX_TRAINS_PER_DIRECTION` trains and hands every platform's arrivals document to `state/`, and every platform to its tick listeners; a platform without a table is skipped, and the tick then rejects with `SUBWAY_TIMETABLES_UNAVAILABLE`. It also builds a platform's timetable-only document. Its writer is `SubwayStateService` (`state/`): it upserts only the documents an arrivals write is due for, remembering the last written ones in the poller process, and only once their write resolved. Atlas bills by peak operations per second and most ticks change few platforms, so writes follow changes, as `history/` stores events only at served platforms.
- `matching/` holds `SubwayMatchingService`, which registers a run matcher with the tracker and keeps each `trainset` line's matches in the poller process: an event whose destination, or else whose reported direction, names a direction is renumbered as its run, any other dropped and counted in a throttled `subway.matching.unmatched` line.
- `history/` holds `SubwayHistoryService`, which listens to the tracker's ticks: it stores each source's first report of a train's state at the served platform itself in `subway_events`, records the served arrival in `subway_predictions` when a train's lead first falls to each of `PREDICTION_HORIZONS_MIN`, resolves a train's records made before the tick that first sees its approaching or arrived row at the station (an arrived row also replacing an approaching row's resolution), within `UNRESOLVED_AFTER_MS` of their predicted arrival, and marks a record unresolved `UNRESOLVED_AFTER_MS` past its predicted arrival. Each tick writes in batches; a failed write is logged and never fails the tick. `SubwayHistoryController` serves the accuracy report behind the internal token; its aggregation is `toAccuracyPipeline`.
- `arrivals/` holds the route and `findSubwayStation`. It reads the topology first, so a never-read one answers `503` with no `Cache-Control`; it then reads the station's coords, served `null` without them; a platform that needs its timetable and has none answers `503` `SUBWAY_TIMETABLES_UNAVAILABLE`, while live arrivals never need one. For each platform of the station, `SubwayPlatformArrivalsService` (`platform-arrivals/`) serves the stored document while it is at most `MAX_STATE_AGE_MS` old, whatever `SUBWAY` says, else the tracker's timetable-only document, so each line falls back on its own, with labels in the request language. It serves each stored train as the call (`toCall`), its status and stops away from its stored position, and names each direction's previous and next stations (`findPlatformName`); `listPlatformCalls` gives one platform's trains as the same calls to the journey's door.

Adding a station touches `src/subway/subway.constants.ts`: the station's slug, names, `seoulName` and campus (`hssc` or `nsc`: the campus the app's station search files it under, kept by hand in step with the `transit-layout` section that lists it, which no check ties to it; null for a station a journey only boards or alights at, which the layout need not place), per platform its KRIC id checked against the code list, its line, its `statnId` and `frCode` from a captured API row and station info answer added to `__tests__/nest/subway/fixtures/` (`subway.constants.spec.ts` checks both) and its timetable source, and the line, when it is new, with its display data and Seoul ids; then the `subway-topology` dataset, pushed from that checkout after the deploy, since a push ahead of it drops the neighbor entry the running code names the stop by (each direction's name, upstream, watched and next platforms, and each neighbor's line, Seoul name, train-map name where the map writes another and localized name where it is a previous or next station or a journey ride passes it; [edit-runtime-data.md](../how-to/edit-runtime-data.md#edit-subway-coverage)) and, pushed before the deploy, the `transit-layout` dataset (the station placed exactly once; [configure-home.md](../how-to/configure-home.md#transit-layout)) and the `subway-station-coords` dataset (the station's coords; [edit-runtime-data.md](../how-to/edit-runtime-data.md#edit-a-subway-stations-coords)); `scripts/subway-timetable/convert.py`: the platform, its upstream platforms and its watched platforms in the timetables it writes, then a rerun whose tables are pushed from that checkout, a new line's ahead of the deploy ([update-subway-timetables.md](../how-to/update-subway-timetables.md)); `src/subway/timetable/subway-timetable.rules.spec.ts` pins the platform's line and source and the topology fixture's directions, `src/subway/timetable/subway-timetable.service.spec.ts` checks those against the timetable's route (the watched ones as the rest of it before the platform, no run between two tracked stops longer than the longest express run, every train in view for ten minutes or from where it starts), and `src/subway/arrivals/subway-arrivals.rules.spec.ts` pins the station and its neighbors' names in every language.

Adding a provider touches a sibling sub-module named after its jurisdiction, holding its clients and mappers, and a poller that hands each of its upstreams to `SubwayTrackingService.track` as a `SubwayProvider` whose observations name their source; the lines it serves, with their ids for that provider beside or in place of `seoul`, since each platform has exactly one provider; and `src/app.module.ts` for the sub-module, and this doc's Context and Glossary for its upstreams.

## Invariants

- A station is identified only by its slug and a platform only by its platform id, each frozen once served, even when a later KRIC list recodes it (the owner renamed one on purpose: Sungkyunkwan Univ.'s `KR-1-0153` became its KRIC code `KR-1-P153`, which `subway_arrivals`, `subway_events` and `subway_predictions` key their documents by); a provider's own ids live under that provider's key of the line (`seoul`), and each platform has exactly one provider, chosen by the jurisdiction of its data.
- The network's identity issues (a repeated station, platform, line or `subwayId`, a platform on an unlisted line or a second one of a line at a station, a line no platform uses) fail its spec and every topology push. A topology push is refused on every issue: a served platform with no entry or an entry for none, a named platform neither served nor a neighbor or on another line, a previous or next neighbor without a name, a neighbor on a line the code does not hold, a train-map name on a line with no map, a neighbor's station id that a served station has or that comes without coords (or coords without one) or without a name, more than three upstream platforms; once those pass, a direction off its platform's timetable route in the target database's stored `subway-timetables` as the next invariant states it, or a stop on that route before the platform neither served nor a neighbor (`toRouteIssues`), and a push to a database storing no tables the checkout can read. With no good topology the route answers `503` and each Seoul tick rejects before any call.
- Upstream platforms are listed nearest first, at most three per direction, and they and the next platform are the route's neighbors of the platform in the timetable. Watched platforms continue the upstream ones on the route, nearest first, to its end; they only feed the tracker: a train there has no stops away, and no call is made for them, since positions are one call per line. Each line's route skips no station between its served platforms and reaches far enough that a train is in view ten minutes before a served platform, the longest prediction horizon, or from where it starts (line `2`'s inner circle at Jamsil excepted, the reference says why): a gap is a stretch where the tracker loses the train, and on a line that reports no departure it holds the train at the station before the gap, late.
- A slug that `findSubwayStation` does not find is not served, a platform id included: the route answers `SUBWAY_STATION_NOT_FOUND`.
- Each platform has its own arrivals document and falls back to its timetable on its own, so a station's lines may differ in `generatedAt` and source.
- Timetables are generated by `scripts/subway-timetable/convert.py` and stored only by `npm run data`, never edited by hand; a push is refused while a served platform lacks a table for a day type its source declares, or while a stop time at a served platform falls outside the service window of its table's day type (`toServiceWindowIssues`), since the tracker never observes it: `SERVICE_WINDOW_*` widens in code and deploys first.
- A train event happens at a station the row names as reached: the API's `trainSttus` `3` and the train map's moving status name the station a train is heading for, so they become no event; nor does a row at a station outside a line's station table, while a duplicate row stays, for the tracker to resolve.
- One upstream tick is read as one response: its responses cover lines whose train numbers never overlap, so the newest row per train within it counts.
- A row of the Seoul API counts for a served platform only by that platform's `statnId`, never by the name it writes, and for a neighbor by its Seoul name; an arrival row counts only for the platform of its own `statnId` at the called station, and only inside the arrival-row window: a row of a line the station does not serve, dated ahead or frozen (a line `K1` row can keep its time for minutes while its text advances) is dropped. `arvlCd` is never read: line `8` marks rows several stations away as arrived.
- A provider hands the tracker timetable numbers: each row's number is read by its line's numbering, and a number the numbering refuses drops the row.
- Within one tick each call settles on its own, and each line's train-map blocks parse on their own: what answered is tracked and the tick then rejects with the first failure; a tick whose every call or line failed, or whose one train-map request failed, is not tracked, so it replaces no countdown rows.
- A train-map line with no train is not a failure until it has had none for over `MAX_EMPTY_LINE_MS` of crawls at most `MAX_EMPTY_CRAWL_GAP_MS` apart: each morning a line is empty for a while after the window opens, and the overnight closure starts a new spell.
- A timetable destination is the name the train map and the Seoul API write for it: `convert.py` refuses a Korail destination in neither of its tables, and one naming trains of both directions unless the line declares it (`__tests__/nest/subway/subway-timetable-convert.test.ts`). A train's direction is its destination's where the day's table runs that destination one way only, else its number's parity, even up and odd down: line `2`'s circle trains, which the API sends to `성수` both ways, go by parity. A trainset number has no parity, so on a `trainset` line the row's reported direction decides instead, never over a one-direction destination: a train leaving a terminus keeps its old `updnLine` for a while.
- A train's latest progress is at a station its timetable row calls at, or, before its first row stop or on its run into its stop at the served station, at a station it passes, measured against its passing stop: elsewhere an event at a station it passes never replaces an observed stop event, and an observed departure keeps its earlier time.
- A sighting counts whatever its delay: a train seen leaving or past the served station is gone, and the delay range only says whose delay an estimate may use. A train seen at or past it is held `PASSED_TRAIN_HOLD_MS`, `MAX_DELAY_SEC` plus the most `MIN_DELAY_SEC` lets a train be early, after it was last seen, so neither a lent delay nor the awaited-train rule lists it again, unless it was seen there earlier still and then vanished from every source; any other missing train is held `MISSING_TRAIN_HOLD_MS`, longer than the longest scheduled run between two row stops, an express from 가산디지털단지 to 안양 (`MAX_UNOBSERVED_RUN_SEC`), which no upstream reliably reports in between.
- On the tracker's path an overdue train with a row stop before the served station that nothing has seen at or past it is awaited: the served station's arrival is observed (every train of the first day's records), so it is late, served now plus its scheduled run from its first row stop, until its scheduled departure plus `MAX_DELAY_SEC` passes or a later train of the same kind (express or local: a local may overtake a late express) is seen at or past the station. The timetable-only document never awaits a train.
- Each upstream ticks, fails and reaches its daily ceiling on its own; a ceiling rejects that source's ticks until the next KST date.
- `SUBWAY=off` stops the subway pollers of the process that sets it, so nothing there calls the provider, and changes nothing the route reads: an api replica with it off serves what the poller stored, and with no poller writing the state goes stale and the timetable serves alone ([ADR 0012](../decisions/0012-runtime-roles.md)). The provider itself has no switch.
- A platform's arrivals document is rewritten only by an arrivals write: `MAX_UNCHANGED_WRITE_AGE_MS` is half of `MAX_STATE_AGE_MS`, so a platform the tracker ticks is never served stale, and a restart, which forgets the last writes, writes every platform on its first tick.
- The train histories live in the poller process's memory and a restart rebuilds them from the next ticks; `subway_arrivals` holds absolute instants and positions, and stops away are computed per response.
- A response carries arrival instants, never seconds left, and `meta.serverNow`: the app counts down against the server's clock, as on the bus routes.
- A source's countdown rows count until its next tick replaces them, and none after `MAX_COUNTDOWN_SOURCE_AGE_MS` without one.
- A countdown counts from its first publication until its instant passes, and not when it implies a delay outside `MIN_DELAY_SEC` to `MAX_DELAY_SEC` against the train's scheduled arrival, as for a train not running yet; a countdown a served train does not count is logged with its reason.
- A train last seen approaching or arrived at the served station is served at its observed arrival, whatever its delay, ignores its countdown, and is gone `MAX_STANDING_PAST_DEPARTURE_SEC` past its estimated departure, its scheduled departure plus its delay at arrival: on line `K1`, which no source reports departing, that is the only way out.
- The countdown memory lives in the poller process and only the tracker's ticks advance it, never a timetable-only document; a restart counts each countdown from its next row.
- Every served train is a scheduled one: a train only in countdown rows or in a history, absent from the day's timetable, is not served. On a `trainset` line that holds through run matching: the tracker sees only runs, and a tick of such a line rejects with no run matcher registered rather than serve trainset numbers as trips.
- Only `SubwayModule` binds the rate limiter for `subway`.
- No upstream error carries the request URL, its config or the original error: the API key sits in the path.
- The accuracy history is written only where the tracker ticks, the poller process, after the arrivals are written, and its events only at served platforms: the upstream, watched and next stops feed the tracker and are never stored; both collections expire after `HISTORY_TTL_SEC`. A failed history write is logged at most once per `WRITE_FAILURE_LOG_INTERVAL_MS` and never fails a tick or changes what is served.
- A prediction is recorded only on the tick a train's lead crosses a horizon, so a train first seen inside a horizon gets no record at it, and a restart skips the horizons crossed before it. It is resolved only by an observation first seen at a later tick than the one that made it (`isResolvableBy`), so it is never measured against the row it was predicted from; an arrived row replaces an approaching row's resolution, and no record is written for a horizon first crossed once the train is seen arrived.

## Open questions

- Whether `recptnDt` is an event time on line `1`, and any offset to apply, waits on the first days of `subway_events`.
- A countdown's divergence from the estimate is logged, not stored with the prediction: the report compares `live` and `estimated` only across trains.
