# Where code goes

ADR 0010 (`docs/decisions/0010-server-architecture.md`) is the decision; `src/building/` is the reference module. What a test or ESLint checks is not restated here: file roles and names, one role file per folder, sub-module direction, Mongo syntax only in repositories and `.query` files, repository return types, route order, limiter coverage, per-role size caps. This file holds the placement rules that need judgment.

## Three questions for new code

1. **Which flow is it?** An endpoint, a poller, or a step one of them takes. Code for a flow lives in that flow's folder. If the folder already has a file of the role you need (a second repository, mapper, controller or rules file), the flow is a sub-module of its own: `src/<module>/<flow>/<module>-<flow>.module.ts`, imported by `src/app.module.ts`, importing its parent. Once a module has a sub-module, its first flow moves into a folder too (`src/building/catalog/`); the root keeps the module file and the code several flows share. Do not make folders by type (`controller/`, `services/`): the explorer nesting in `.vscode/settings.json` groups a folder's files instead.
2. **Which role?** Talks HTTP: controller. Composes a use case: service. Reads or writes Mongo: repository. Builds Mongo syntax without running it: query. Calls a third party and translates its payload: client. Decides or computes: rules. Reshapes: mapper.
3. **Who already owns it?** One concept has one home. Search the module's glossary in `docs/explanation/<module>-architecture.md` and its files before adding a new name or helper.

## Rules that need judgment

- **Joins are the service's.** A repository method runs one query and returns documents or a projection of them. When a response needs two reads (a building's connections and the buildings at their far ends), the service makes both calls and a mapper puts them together.
- **A projection belongs to the flow that reads it.** The root's `.document` holds each collection's shape, which several flows share. A `Pick` that only one flow's queries return lives in that flow's `.document`: `ConnectionEnds` in `src/building/catalog/building-catalog.document.ts`.
- **An index belongs to the repository whose query it serves**, created in that repository's `onModuleInit` through `ensureIndexesAtBoot` (`src/infra/mongo.ts`). An index that guards a write (a unique key an upsert filters on, a 2dsphere that rejects malformed geometry) belongs to the writer. An index that neither serves a query nor guards a write is not created: check `$indexStats` before keeping one.
- **Rules, mapper or query.** A rule decides or computes (`toDisplayNo`, the tier tables). A mapper reshapes without deciding (`groupByFloor`). A query writes Mongo (`tiersToScoreExpr`). When a rule must reach the database, split it: the decision stays in `.rules`, its Mongo form goes to `.query`, and a spec pins that the two agree.
- **A pure function that builds Mongo syntax is still Mongo.** A `$set`, a filter or a bulk operation belongs to the repository or a `.query`, never to a mapper.
- **Flows read the parent's repository; other features read its service.** A sub-module injects its parent's repository directly. Another feature may import only a module's `.module` and `.service` files, so a module that others read exports a service as its door, and that service may forward to the repository 1:1 (ADR 0010, D1): `BuildingService` for `map`.
- **Only the module that owns a URL prefix binds the rate limiter.** A sub-module under the same prefix binds nothing, or each request counts twice.
- **A committed config file fails the boot with every issue.** The flow's `.config` parses it through `parseConfigFile` (`src/infra/config-file.ts`), which throws all its issues, each with its path, in one line (`config-files` checks the call). It parses at import, or, when the check needs another provider (ui's registry check against `MiniAppsService`), when Nest builds the provider that reads it: `src/ui/home/ui-home.config.ts`. `src/map/layer-set/` still parses at import and reports only the first issue (exempt in `__tests__/architecture/exemptions/config-files.json`); new code copies ui.
- **Data written outside `src/` is parsed where it is read, in the repository, always.** Its type in the `.document` carries the `CONTRACT(<writer>):` tag. The read passes a literal `projection` of the fields its flow uses and parses the result through a zod schema in `.schema` that `satisfies` the type it returns (`parseEach`), leaving out and logging a bad document; a fake parses the same way. Check what makes a document unusable, and pin the writer's output against the schema in a test. `repository-reads` checks the projection and the parse.
- **Which side of a boundary a shape sits on.** A shape that a deployable of this repository writes and another repository reads (an HTTP response body, a push payload, a document or config file another repository reads) is defined in a `.wire` file, and its type comes from there, not from `.types`. A shape that only this repository's deployables write and read (`bus_cache`, written by the poller and read by the api) has one definition in `src/`, imported and never exported. A shape another repository writes is generated from that repository's export, never restated (ADR 0010, D13).
- **A `.schema` wraps a wire schema, never the reverse.** Brands, transforms and refinements stay in the `.schema`, which imports the wire schema and extends, pipes or refines it. Publishing a shape never changes what is served: a backfilled wire records the response as it is today, unread fields included.
- **Characterize before moving a Mongo shape.** Pin the exact operation on today's code in a spec, then move it; the expected value must not change in the move.
